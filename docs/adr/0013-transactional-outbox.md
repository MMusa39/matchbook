# 0013: Transactional outbox and idempotent consumers in post-trade

**Status:** accepted

## Context

Two places in the system must change state and publish an event *together*:

1. **The engine** matches an order (its state) and must get the resulting trades and executions to
   Kafka.
2. **Post-trade** updates a position in PostgreSQL and must publish `PositionChanged`.

Doing "write, then publish" as two separate steps loses the event if the process dies in between.
"Publish, then write" announces something that never happened. Distributed transactions (XA across
Kafka and Postgres) are slow, fragile, and in Kafka's case not available. Every hop is therefore
**at-least-once**, and every consumer must be **idempotent**.

## Decision

### Engine → Kafka: the journal is the outbox

The engine already writes every command to its journal before matching (ADR-0005), and matching is
deterministic (ADR-0008). So the trades and executions of any journaled command can always be
regenerated by replay, and the journal *is* an outbox.

- **What Kafka has:** `KafkaAckTracker` follows, per journal sequence, how many Kafka records are still
  unacknowledged. The *acked floor* is the highest sequence whose command's records are all
  acknowledged, counting only commands whose records were all handed to the producer. It is
  persisted every 200 ms.
- **Restart:** the pipeline recovers from the newest snapshot *at or below the floor*, so every event
  Kafka may be missing is replayed and re-sent. Snapshot pruning always keeps that snapshot and the
  journal after it (`PipelineConfig.replayFloor`).
- **Dedupe headers:** every record carries `mb-shard` and `mb-seq`. The pair is unique and stable
  across replays, because sequence numbers are deterministic.
- **Producer settings:** the Kafka producer is idempotent (`enable.idempotence`, `acks=all`), which
  removes duplicates from producer retries within a session.

### Post-trade: idempotent consumer + transactional outbox

For each trade record, one Postgres transaction does all of the following:

1. `insert into processed_events (shard, seq) … on conflict do nothing`. If no row is inserted,
   the event was already applied, and the transaction stops here.
2. Insert the trade, then lock both clients' position rows in a fixed order (no deadlocks) and update
   them using average-cost P&L.
3. Insert one `outbox` row per changed position.

The Kafka offset is acknowledged only after commit (manual ack). A crash anywhere means redelivery,
and redelivery is harmless.

`OutboxRelay` publishes outbox rows every 100 ms:
- it locks a batch with `SELECT … FOR UPDATE SKIP LOCKED`, so several relays can run without
  double-sending;
- it waits for broker acks, then marks the rows published, all in one transaction;
- records carry `mb-outbox-id` and the position `version`, so downstream can de-duplicate and drop
  out-of-order updates.

Poison records, which can never be parsed, go to `<topic>.DLT` after a bounded retry, so they don't
block their partition.

## Verification

- `PostTradeIT` (Testcontainers Kafka + Postgres): duplicate delivery is applied once, outbox rows reach
  Kafka with their id header, a poison record lands on the DLT, and later records still flow.
- `KafkaAckTrackerTest`: floor semantics, including a command whose first record was acknowledged
  before its second was sent.
- `KafkaPublishingIT`: records carry the dedupe headers and the caller's `traceparent`.

## Consequences

- A restart can re-send a bounded window of events: everything after the acked floor. Consumers must
  de-duplicate, and ours do.
- If Kafka is down for long, the floor stops moving, and snapshots behind it accumulate (they are not
  pruned). If it is down for very long, the outbound ring fills and the engine stops accepting orders.
  That is deliberate: a venue should not keep trading without its drop copy.
- `processed_events` grows by one row per event. It needs a retention job keyed on the snapshot/acked
  floor, which this project leaves out (noted in DESIGN.md).

## Alternatives considered

- **Kafka transactions with read-process-write:** exactly-once within Kafka, but our state lives in
  Postgres.
- **Debezium/CDC on the outbox table:** a fine production choice that removes the polling relay. It
  needs another running service, so the polling relay is used here.
